# Learn data science by predicting house prices: full course, beginner to professional — plan

**Status: v1 plan, approved with two decisions (2026-10-27): FastAPI for the API; Python stays 3.15.1
(every library had a cp315 wheel). All 11 courses (71 sections) authored 2026-10-27, awaiting owner
review — see "As authored" at the end for where the build departed from this plan, and why.**

## The idea

One question, **"what is this house worth?"**, and one application, `house-prices`, that answers it.
The work starts the way data science starts, in a **notebook**, with a messy CSV of house sales. It ends
the way data science ships: as a tested Python package with a command and a small web API that values a house,
`£212,000 (likely £195k–£231k)`. Every pandas, statistics and machine-learning idea is taught **when
the question first needs it**. Background topics (what a notebook kernel is, the bootstrap, leakage,
least squares) are short detours at the moment they answer something on screen.

Why house prices:

- **Nothing to explain.** Everyone knows that a bigger house, a better area and a garage cost more.
  So learners can judge whether a result makes sense before any statistics.
- **It exercises the whole toolkit.** It has numbers (size, year built), categories (area, heating),
  dates (sold), a table to join (area facts), real missing values, real outliers and a skewed target.
- **Each question pulls in the next tool:**
  - "What do we have?" needs DataFrames.
  - "Can we trust it?" needs cleaning.
  - "Which area costs most?" needs groupby and joins.
  - "Does a garage add value, or is that luck?" needs statistics.
  - "What is THIS house worth?" needs models.
  - "How wrong could we be?" needs validation and intervals.
  - "Use it every day" needs a package and tests.
- **The frame evolves with the work.** Courses 2–10 are in a notebook, which is where exploration
  happens. Course 11 moves the same code into a package in the IDE frame. That move is itself a lesson:
  notebooks are for asking questions, modules are for running answers.

## Packaging for YouTube

**One video: "Learn data science by predicting house prices: full course, beginner to professional"**:
11 courses, ~71 sections, ~2 h 30 min, one continuous story. It opens with the finished command
valuing a house (the payoff first). A course is one YouTube chapter group and the owner's review
unit; a section (90–150 s) is one chapter, titled *concept: what we learn about the houses*
(e.g. "groupby: which area costs most"). Each section can also go out as a Short (`record-reels`).

**Prerequisite:** Python basics — the expense-tracker video. Not re-taught here; a section that leans
on it says so in one line (e.g. "a comprehension, as in the expense tracker").

## The data: Millbrook house sales (synthetic, owned)

One fictional town, **Millbrook**, its sales from 2021 to 2026. The data is generated by
`data/generate.py` (seeded and committed), so it is ours, reproducible and free to publish.

- `data/homes.csv`: ~1,460 sales. Columns: `id, sold, area, sqft, lot, beds, baths, built, garage, condition,
  heating, price`.
- `data/areas.csv`: one row per area: school rating, km to the centre, flood zone. Joined in 5.4.
- `data/listings.csv`: 20 unsold houses, valued in Course 11.

**The faults are planted on purpose**, and each one is a lesson:

| Fault | Taught in |
| --- | --- |
| `"£215,000"` as text in `price` | 4.3 |
| one agent's batch in m², not sq ft | 4.4 |
| `garage` empty = no garage, not unknown | 4.2 |
| the same sale entered twice | 4.5 |
| a 12-bedroom typo; a £10k family transfer (not a market sale) | 4.6 |
| dates in two formats | 3.6 |
| an area spelled `Old town` vs `Old Town`, so it fails the join | 5.4 |

**Prices come from a known rule plus noise** (size, area, age, garage, condition), and the rule is
written in `generate.py`. So in 9.4 the course can show something real data never could: the model
recovers the £-per-sq-ft we planted. The rule stays hidden until then, and the narration admits it
honestly as the payoff.

## The app: `house-prices`

One name everywhere: the folder, the project and the command are `house-prices`; the importable
package is `house_prices`.


## Frames

- **Notebook frame** (new in graphl-flow 0.4, `notebook-frame.ts`): explorer | notebook (cells:
  `[n]` gutter, input, output as text, DataFrame `table` or `plot`) | the fixed side pane. Every
  notebook frame has the same floors, so they all get the same zoom. There are no edges between panes.
- **IDE frame** (Course 11): the expense tracker's template, unchanged.
- **Concept scene** (◆ full scene): a canonical big picture that cannot fit the side pane at
  ≥ 24px body text. It carries the real output inside as a `code` or `table` node from a lab step.

**Every side pane carries a diagram**: a DataFrame picture, a plot, a pipeline or a result table.
Never a bullet list.

## How a section teaches

Objective → mental model (side pane) → the code and its real result → a failure or alternative →
bridge. One step per section; a failure is its own step, with a real traceback or a real wrong
number. Narration explains and never reads code aloud. A detour ◆ is ≤ 120 s and returns to the
houses. Numbers that are random (bootstrap, splits) are seeded, so they replay exactly.

## The spine

As in python-expense-tracker: `spine/<course>/<NN-step>/` = `project/` + `session.txt` + `step.json`,
plus **`cells.json`**: the step's notebook executed headlessly (`jupyter nbconvert --execute`), with
each cell's outputs. Scenes read a cell's output from it, and never type one. A DataFrame output is
taken from its plain-text form and becomes a `table`; a plot node's numbers are values the cell
printed or saved. Timings stay `volatile`, as in the expense tracker.

## As authored (2026-10-27)

Where the authored course departs from the tables above. Each departure came from a real output.

- **One notebook per course** (tree above), not one explore.ipynb for Courses 2–6: cell counts stay
  short enough to read, and Course 4 hands the next courses a file (`homes_clean.csv`), as real work does.
- **2.1 is an IDE frame** (terminal + pyproject.toml); the notebook frame starts at 2.3.
- **3.4**: "price per sq ft" is attempted and fails for real (price is still text); it works in 5.2.
- **4.2**: `built` stays missing (no invented years); the median is imputed inside the model pipeline (8.6).
- **4.7, 5.5, 7.3, 8.3, 9.3** are full scenes built from the notebook cells' real output (no separate labs).
- **6.4**: medians with the middle half drawn by `vlines`, not a box plot.
- **7.5**: the permutation test is written by hand with NumPy (`shuffled_differences`); SciPy checks the
  bootstrap in 7.4.
- **9.5: the log target LOST** (6.2% vs 7.0% typical miss) and is dropped. Prices here are built additively.
- **9.7: the plain linear model beats gradient boosting** (£19,925 vs £21,292), and still does after tuning
  (10.2). The linear model is the one shipped.
- **10.5: quantile boosting's 10–90% band held only 67% of test prices**; the shipped interval is the linear
  model ± its cross-validated errors (held 84.2%).
- **Course 11** has `value.py` (the one function behind the command, the batch and the API) and the
  training script reproduces the notebook's test MAE exactly. The interval offsets and the training
  ranges live in `models/model.json`; `value()` refuses unknown areas and sizes outside the data.
- **The finished valuation** (Course 1's payoff) is the real one: a 1,710 sq ft Riverside house, built
  2004, two garages: £383,000 (likely £350k–£417k).
